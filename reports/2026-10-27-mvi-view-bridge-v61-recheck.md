## 判定 2：修订有无新破坏

### N1（Major）§8 重定基记账自相矛盾：~740 ≠ 自己的账本

- 证据：标题 L614、记账 L616、合计行 L632 三处盖 **~740（PM 预批）**；同一节链式明细「核心 ~400 → +60 → +40 → +145 → +90 → **v6.1 +100（入总账）**」加总 = **835**；文件表逐行直加（含 manifest ~20 + gen ~80）= **838**。三组数互相矛盾。charitable 读法（~740 = 截至 v6 的 738 取整）与文本冲突：「合计（产品切片口径）」按定义必须含全部表行，「实现期按 ~740 额度收口」按定义约束总支出。
- 为什么是 Major：这不是排版瑕疵——按裁决②，这个数字将原文进入「用户终批 + ADR 0006 拍板包」。批准覆盖 ~740、计划支出 ~838，差 ~100 行无批准记录——与原 Major 2「承诺与合计矛盾」同一缺陷类，只是从「无批准」变成「批准数与账本不符」。封版文档的合计不可与自身明细矛盾。
- 修法（不改裁决原文，只修文档算术）：三处口径与表格逐行和对齐。建议形态：**合计 = ~840 = ~740（PM 预批重定基数，截至 v6 口径）+ ~100（裁决③ M3 执行件：gen ~80 + manifest ~20）**；标题/记账/合计/回落触发额度四处同改；recount 时把 demo `include_str!` 对表断言的行数增量一并计入（v6.1 链只记了 gen+manifest，demo 增量未入账）。若 PM 的 ~740 本意是含 v6.1 的总账数，则 ~100 差额须由 PM 重认（砍 M3 或移另计），**不得由文档私自吸收**。

### N2（Minor）delivered_epoch 的快照推进语义欠一句

- 证据：`from_version` = 「上一次 JSON 交付的 to_version」（L252、L349），而「JSON 交付点」在 L121/L167/L296 反复写明 = **take_patches 与 snapshot_doc 两处**——按此读法快照即交付、游标随快照推进，算法闭合。但 (a) 的 delivered_epoch 定义处（L349）与 (c)/(b) 均未写明「snapshot_doc 推进 delivered_epoch」，断言链①（L638）也无一条断言钉住它。若实现者把「交付」只读作 take_patches：毒化恢复路径（MVP 断言链②，L644）中 take_patches 与 snapshot_doc 之间落一拍 dispatch，则 `from_version` 永远追不上 `applied_version` ⇒ 每拍误判缺段 ⇒ 每拍全量重投影（正确性不破、增量设计失效 + demo 断言链①的 `from_version == 上一批 to_version` 在混用快照时翻红）。
- 修法：L349 补一句「**快照即交付：snapshot_doc 将 delivered_epoch 推进至当前消费代数**」（或等价）；断言链① 增一条「snapshot_doc 后次批 `from_version == snapshot.version`」。两处合计一句话 + 一条断言。

### 扫过无破坏的点（列证据，非走过场）

- **消费代数跨桥重建/Drop 连续性**：桥 Drop = 票据注销；重建后新桥代数从 0 起，UI 旧 `applied_version` 必触发 (b) L364-366 倒退分支或 L367-369 缺段分支 ⇒ snapshot_doc 重建基线自愈（配合 N2 修法后无副作用循环）；跨桥/跨进程不同源已在 L347 + §12-12 L728 显式划出承诺边界（「不在本方案承诺内，未来须跨桥共享版本源，属新 ADR」）。语义闭合。
- **同 store 多通道同源边界**：L346 两通道取同一桥内代数 ⇒ 可直接互比（撕裂检测唯一依据）；跨桥不同源边界见上。声明完备。
