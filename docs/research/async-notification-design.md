## 1. 问题陈述（现象 → 事实 → 影响面）

**现象**：状态订阅者的回调在 dispatch 线程内**同步执行**，慢订阅者直接拖住整个状态机。

**树内事实（可复核）**：

| # | 事实 | 证据 |
|---|---|---|
| F1 | 契约层承诺「回调在 dispatch 线程同步执行」 | `skeleton/src/lib.rs:373`（Store 语义契约第 3 条）、`:429`（`fn subscribe(&self, f: impl FnMut(&Self::State) + Send + 'static) -> Subscription<Self::State>`） |
| F2 | 通知调用点在**排空环体内**（每拍一次） | `skeleton-infra/src/runtime.rs:1081`（`notify_snapshot_consumers(inner, cache, &notified_next)`），位于 `drain_owned`（`:967`）的循环体内 |
| F3 | 排空环管线序 = reduce → 快照落位 → 效果转发 → 通知 | `runtime.rs:1070`（`place_snapshot`）→ `:1079`（`forward_effects`）→ `:1081`（通知） |
| F4 | 通知体执行用户闭包（跨线程档在槽位 Mutex 内调用） | `runtime.rs:1168-1213`（`notify_snapshot_consumers`）、`:1192-1200`（`catch_unwind` + 摘除 + `subscriber_panics`） |
| F5 | 订阅回调内 dispatch 被计为**回灌深度**（受 64 预算约束） | `runtime.rs:241`（`FEEDBACK_DEPTH_BUDGET = 64`）、`:286`（`reentrant_origin`）、`:267`（`ReentrantDepthGuard`） |
| F6 | 慢订阅者有实测代价：1 MiB State 的深克隆 ≈ **210 µs/dispatch** | 审计报告 F-05（`reports/2026-10-27-udf-architecture-audit.md` §3 F-05 实测段） |
| F7 | 存在**两档**订阅面（跨线程 / 本地线程亲和），本地档他线程 dispatch **不触达** | `runtime.rs:691`（`subscribe_local`）、`skeleton-infra/src/runtime/local_subs.rs`（TLS 表）、`skeleton-infra/tests/api_polish.rs:196`（`subscribe_local_notifies_only_on_registering_thread`） |
| F8 | 性能锚：无订阅 ≈ **77 ns**、订阅态全含 ≈ **142 ns** | `README.md:144`、`docs/reference.md:196`（2026-10-16 批 C 实测） |
| F9 | 快照落位用 `Arc::make_mut` **就地改写**（外部持有者 ⇒ 每拍深克隆 `S`） | `runtime.rs:1097-1113`（`place_snapshot`：`mem::replace(Arc::make_mut(&mut slot), next_val)`） |
| F10 | 审计事件链在通知点交织（`Notified` 与 `Reduced`/`Enqueued` 逐拍交错），有测试钉死交错序 | `runtime.rs:1082-1085`（发 `Notified`）、`skeleton-infra/tests/journal_port.rs:305-330`（交错链逐字断言） |
| F11 | 通知顺序对订阅者可观测（reduce 序 → 通知序） | `skeleton-infra/tests/store_behavior_gaps.rs:225-243`（一 dispatch 内回灌 ⇒ 通知序 `[1, 11]`） |
| F12 | `runtime` feature **零三方**（依赖树只有 `skeleton`/`std-ext` 路径依赖） | `skeleton-infra/Cargo.toml`（`runtime = []`）、ADR 0004 |

**影响面**：

1. **排空环被订阅者绑架**：一个做 IO/渲染的订阅者，让后续 action 的排空（连同 Emit 回灌链）全部排队等待（F2+F3+F4）。
2. **dispatch 延迟不可控**：调用方无法区分「状态机慢」与「订阅者慢」（F2、F8）。
3. **异步化不是加一个 API 就能解决的**：现有通知**语义**绑定在「同步执行」上——订阅回调内 dispatch 依赖回灌深度预算（F5），审计链绑定通知点（F10），通知顺序对订阅者可观测（F11）。任何改动都要同时裁决这三条。

**本稿要回答的问题**：在不破坏上述语义契约的前提下，给出「订阅者通知不阻塞 dispatch 排空环」的**可选形态**，并说清每种形态的破坏面、回滚成本、承重假设。

## 2. 驱动因素（决定结构的力）

### 2.1 质量属性场景（QAS 六元组）

| 元素 | 内容 |
|---|---|
| 刺激来源 | 外部采用方宿主（UI/服务混合栈）与本仓 ViewBridge |
| 刺激 | 订阅者回调执行耗时 ≫ 单拍 reduce 耗时（渲染 / 网络回写 / 大 diff） |
| 环境 | 正常运行期，排空环持排空权、队列非空或单拍 dispatch 中 |
| 受体 | dispatch 调用方（UI 线程 / 事件循环 / 服务请求线程）与排在后面的 action |
| 响应 | 排空环不执行用户重活；通知以「可合并的状态信号」投递到**宿主自持**的消费侧 |
| 响应度量 | ① 有订阅者时 dispatch 延迟 ≤ 无订阅基线 × 1.2（当前 ≈1.84×，142/77）② 排空环内用户代码执行时间 = 0（结构性，非统计）③ 通知延迟 = 消费侧调度延迟（框架不承诺上界）④ 版本跳跃可被消费侧检出（M5） |

### 2.2 硬约束（不可协商，来自既有设计与纪律）

## 3. 语义公理（异步通知必须满足的 6 条）

这 6 条是从既有语义与外部踩平机制（M1 / M5）推导出来的**判据**，任何候选方案逐条对表；对不上即出局。

| # | 公理 | 推导来源 |
|---|---|---|
| A1 | **投递不得执行用户重活**：排空环内用户代码执行时间 = 0（结构性） | F2–F4；QAS 响应度量 ② |
| A2 | **投递必须是 O(1) 且非阻塞**：投递成本与订阅者快慢无关 | F6（慢订阅者不得传导） |
| A3 | **顺序可恢复**：任一消费侧都能从投递物中恢复「先后」 | F11（通知序可观测）+ M5（版本水位） |
| A4 | **合并（coalescing）语义合法**：中间拍可丢，但**必须可检出丢失** | M1（不承诺投递的事件流 ⇒ 载荷必须状态化）+ M5（版本跳跃 ⇒ 重取而非补齐） |
| A5 | **失败可见**：投递失败/panic/丢弃均有计数或成因面 | C4 |
| A6 | **关闭语义显式**：闭门后登记/投递行为可查 | F7 + 审计 F-10（`subscriptions_after_close` 先例） |

**M1/M5 的直接推论（关键）**：

- **M1**（事件规约成状态：不用不保证投递的事件流）⇒ 异步通知**不能**设计成「每拍一条事件的有界队列」。一旦做成事件流，就会出现「消费者暂停 ⇒ 事件丢失」的结构性缺陷（官方判为违反 ACID）。**载荷必须是状态或状态信号，不是事件**。
- **M5**（帧/拍级一致的水位与版本：出站带版本号，外部状态在渲染中途变化被检测并重跑，绝不撕裂）⇒ 异步通知**必须带单调版本号**；消费侧见版本跳跃即重取（resync），而不是逐条补齐。

> 由此得到本稿的架构主轴：**异步通知 = 「状态水位信号」而非「事件流」**。这是后面所有候选案的筛选器。

## 4. 候选方案（4 案 + 变体轴）

### 4.0 变体轴（用于看清各案差别）

| 轴 | 取值 |
|---|---|
| X1 投递物 | ① 快照 `Arc<S>` ② 版本号（脏信号，消费者拉取）③ 两者 |
| X2 消费侧归属 | ① 框架泵线程 ② 宿主自持（框架只投递） |
| X3 投递时机 | ① 排空环内即时 ② 排空结束后统一 |
| X4 承载形态 | ① 现有 `subscribe` 语义改写 ② 新增独立端口（现有语义不动） |

四案的差别是**结构性的**（数据所有权/边界/控制流），不是换库换名。

---

### 案 A：排空后统一派发（X3=②，X4=①）

**机制**：排空环内不再执行订阅者回调，改为把每拍的 `(订阅槽, Arc<S>)` 收集进本地缓冲；排空环退出（队列空）后，在**同一 dispatch 线程**上按登记序 × 拍序统一派发。

**数据流**：reduce → 落位 → 转发 → **收快照入缓冲** →（排空环退出）→ 统一回调。

**破坏面**：

| 面 | 影响 |
|---|---|
| 契约文本 | Store 契约第 3 条「回调在 dispatch 线程同步执行」**字面仍成立**（仍在 dispatch 线程、仍在 dispatch 返回前），但「同步」的时刻从「逐拍」变为「整链后」——需改文档措辞 |
| 审计链 | **破坏**：F10 的交错链（`Notified` 夹在 `Reduced`/`Enqueued` 之间）会变成「整链后才 Notified」→ `tests/journal_port.rs:305-330` 逐字断言**必须改** |
| 回灌预算 | **新病理面**：F5 的深度计费依赖 `ReentrantDepthGuard` 在通知时仍生效；统一派发发生在守卫恢复之后 ⇒ 订阅者回调内 dispatch 被判为 `External`（`runtime.rs:286`）⇒ **反馈预算不再约束订阅者驱动的环** ⇒ 订阅者每次回调都 dispatch ⇒ 新 dispatch ⇒ 新一轮统一派发 ⇒ **无限乒乓**。必须补「派发轮次预算」+ 新计数，等于新增一套失败面 |
| 通知顺序 | 保持（F11 的 `[1,11]` 仍成立），只是延后 |
| 快照一致性 | 保持（每拍 `Arc<S>` 独立快照） |
| dispatch 延迟 | **不改善**：dispatch 仍要等所有回调跑完（只是移出环体）→ 审计 F-06 的核心诉求「慢订阅者阻塞全局」只解决一半 |

**回滚成本**：中。改动集中在 `drain_owned` 的通知段 + 审计链测试 + 新预算计数与文案。回滚 = 还原通知段即可，但已改的测试与新增计数面要一并撤。

**承重假设**：

1. 假设「订阅者只在链末被叫一次」可接受（链中状态不可被订阅者观测）——但 F11 证明链中状态**是**可观测契约。
2. 假设订阅者回调内不再 dispatch（或框架能补上轮次预算）——否则引入无限乒乓。
3. 假设 dispatch 延迟被订阅者主导可接受——与 QAS 响应度量 ① 冲突。

**与 M1/M5 交叉**：载荷仍是逐拍快照事件序列（每拍一条）⇒ 合 M1（顺序+水位）但**违 M1 精神**（未合并的逐拍序列在异步化后必然要合并）；M5 需补版本号。

**什么条件下它更优**：若采用方明确要求「订阅者只在整链结束后被叫一次」（如链中态不可观测是有意设计），A 的实现量最小且不动契约面。

**我猜 A 最可能错在哪**：以为「移出环体」等于「不阻塞」。实际上 dispatch 返回仍被订阅者时长支配，且把回灌预算的护栏挪丢了。

### 案 B：每订阅者独立队列 + 框架泵线程（X2=①，X3=①）

**机制**：每个异步订阅者拥有一条独立有界队列 + 一个泵线程（消费该队列）。排空环内只做 O(1) 入队；回调在泵线程执行。

**数据流**：reduce → 落位 → 转发 → **入队（O(1)）** → 泵线程出队 → 用户回调。

**破坏面**：

| 面 | 影响 |
|---|---|
| 契约 | 需新增端口 + 新票据语义（现有 `Subscription<S>` 语义是「Drop=注销」，泵线程的 join 序要另立） |
| 线程生命周期 | 每个 store 每订阅者一条线程（**线程数 = 订阅者数**）；`close()` 与 store `Drop` 的 join 序、停机时的未消费队列（丢弃 or 冲刷）都要定 |
| 背压 | 队列满时的策略（丢最旧 / 阻塞 / 拒收）直接违 A2（阻塞）或 A4（丢弃需可检出）——需要新计数 + 版本号 |
| 跨订阅者相互影响 | 若改共享泵 + 每订阅者队列 ⇒ 队头阻塞（一个慢订阅者堵住其他人的派发）——违背 A2 的「投递成本与订阅者快慢无关」 |
| 失败面 | 泵线程 panic、泵线程崩溃、队列溢出、停机时未冲刷——每条都要计数（C4），新计数面 ≥4 个 |
| 依赖面 | 线程是 std（不违 C2），但引入「框架拥有线程」这一新事实，与 C7（框架不拥有循环）张力最大 |
| 与 ViewBridge | 桥的通知体（投影 + eager 区域编码）搬出环体可行；但桥的「共享区始终最新」承诺要重述（见 §7） |

**回滚成本**：高。新增线程/队列/计数/停机序，且与已有 `Subscription`/`LocalSubscription` 票据语义并列——回滚要删一整套机器。

**承重假设**：

1. 假设订阅者数量少（线程数线性增长）——UI 场景通常成立，服务端多 store 场景不成立。
2. 假设「丢弃中间拍」对订阅者可接受且可检出——需要版本号（M5）。
3. 假设框架拥有后台线程可接受——与 C7 张力。

**与 M1/M5 交叉**：载荷若仍是「逐拍快照」⇒ 是事件流 ⇒ **违 M1**；若改为「最新值覆盖」⇒ 合 M1，但每订阅者队列退化为单槽 latest-value（此时 A2 的独立性要求自动满足：慢订阅者只影响自己的槽）。M5 需版本号。

**什么条件下它更优**：若采用方要求「框架保证回调一定在框架线程执行」（如需要统一线程亲和、统一 shutdown 编排），且订阅者数量少。

**我猜 B 最可能错在哪**：把「异步」实现成「线程 + 队列」，于是背压、丢弃、停机、未消费这四个问题全部变成框架的新责任，而它们在「状态信号」语义下**根本不存在**。

### 案 C：两档并存 + 状态水位信号（新端口，X1=②，X2=②，X3=①，X4=②）—— **推荐**

**机制**：现有 `subscribe`（同步档）与 `subscribe_local`（本地线程亲和档）**一字不改**；新增一个独立契约端口（`skeleton/src/notify.rs`），登记一个**宿主提供的投递口**；排空环内只做 O(1) 投递（调用投递口），**不执行任何用户重活**；载荷是**状态版本号**（单调递增），消费侧按需 `store.snapshot()` 拉取现态。

**数据流**：

```
reduce → 落位(state_version += 1) → 效果转发 → 通知段:
      ├─ 同步档：现有 subscribe 回调（原地执行，契约不变）
      └─ 异步档：投递口.publish(state_version)   ← O(1)，用户重活在宿主侧
宿主消费线程：收到版本 → store.snapshot() → 自己的重活 → 见版本跳跃即重取（resync）
```

**签名级草案**（skeleton 契约层，零依赖）：

```rust
// skeleton/src/notify.rs —— 状态水位通知端口（契约词汇，零依赖）

/// 状态变更信号投递口：**宿主实现**。框架只调用，绝不在调用内执行用户重活。
///
/// 契约（A1/A2）：
/// - `publish` 必须在 O(1) 内返回，禁阻塞、禁在调用内做 IO/渲染；
/// - 允许合并（宿主可只保留最新版本）——因此**必须**按版本号判定是否跳拍（M5）；
/// - panic 会被框架捕获并摘除该投递口（fail-closed，同步档同一纪律）。
pub trait NotifySink: Send + Sync + 'static {
    fn publish(&self, version: u64);
}

/// 异步（信号式）通知端口：**实现方**（`SyncStore`）实现。
/// 与 `Store` 正交，宿主可同时用同步档与异步档。
pub trait Notify<S> {
    /// 登记状态变更信号投递口。票据 Drop = 注销（复用 `Subscription<S>` 语义）。
    fn subscribe_notify(&self, sink: impl NotifySink) -> Subscription<S>;
}
```

**破坏面**：

| 面 | 影响 |
|---|---|
| 现有契约 | **零破坏**：`Store` 六方法不变、`subscribe`/`subscribe_local` 语义不变、审计链不变、通知顺序不变（F10/F11 断言不动）、回灌预算不变（F5 不动） |
| 新增面 | 1 个新 trait 文件（契约层 ~40 行）+ 实现层注册表 + 版本计数器 + 2 个读侧计数 |
| 性能锚 | 无订阅路径需保持 77 ns：版本自增与异步投递必须**门控**（零异步订阅者时一次 relaxed 读即短路，照抄 `audit_gate` 快路径先例 `audit_emit.rs:56-58`） |
| 快照落位策略 | **必须联裁**：异步档不外发 `Arc<S>`（只发版本号）⇒ 消费侧拉取时短暂持有 `Arc<S>`；若消费侧持有跨越下一次落位，F9 的 `Arc::make_mut` 仍会触发深克隆 ⇒ 见 §6.4 落位策略裁决 |
| 失败面 | 投递口 panic（复用 `subscriber_panics`/`subscriber_panic_last_cause`，不造第二套计数）+ 闭门后登记（复用 `subscriptions_after_close`）——**不新增异常种类** |
| 与 ViewBridge | 桥的通知体重活从 drain 线程搬到宿主消费侧；桥的「共享区始终最新」需重述（§7） |

**回滚成本**：**低**。新增代码集中在独立文件（新 trait + 新注册表 + 新计数）；删掉即回到现状，**既有测试与文档无需回滚**（这是四案里唯一做到的）。

**承重假设**：

1. 消费侧愿意「拉取」而非「被推送快照」——消费侧已持有 store 句柄（`Store::snapshot` 已是既有拉取面，F1 契约 2）。
2. 合并可接受且可检出（版本号）——M1/M5。
3. 宿主消费线程的调度延迟不受框架控制（QAS 响应度量 ③ 明确「框架不承诺上界」）。
4. 同步档回调保持廉价——**异步档不救同步档**：慢同步订阅者仍会阻塞 drain（这是 C3/C6 下的诚实取舍，须写进契约文案）。
5. 版本号 `u64` 自增不回绕（2^64 拍 ≈ 5840 亿年 @ 10 亿拍/秒，实践中不可达）。

**与 M1/M5 交叉**：**完全对齐**。载荷 = 状态信号（版本号），不是事件流 ⇒ M1 合规且不需要「不保证投递的事件流」；版本号让消费侧检出跳拍并重取 ⇒ M5 合规（与桥的 `snapshot_doc` resync 同构）。

**什么条件下它更优**：绝大多数情形——尤其是「采用方自己已有消费线程/事件循环」的宿主（UI 框架、tokio 宿主、服务 worker）。此时框架只提供「状态变了，版本 N」这一个信号，剩下全是宿主自己的事。

**我猜 C 最可能错在哪**：以为「版本号 + 拉取」足够让所有采用方满意。实际会有一类采用方坚持要「框架把确切快照推给我」——那需要 X1=③ 变体（带 F9 的深克隆税，见 §6.4），届时本案的边界被突破。

### 案 D：桥侧自管版本水位（框架零改动）

**机制**：框架**完全不动**。ViewBridge（或任何采用方）自己注册一个**廉价**的同步订阅者（回调只做 `AtomicU64` 自增，O(1)），并在**自己的**工作线程上按该计数拉取 `store.snapshot()` 做投影/编码。

**破坏面**：框架面 **0**（唯一可能新增：`SyncStore::state_version()` 只读计数，供桥侧检出跳拍——否则桥只能用自己的计数，无法感知「自己漏了框架侧的几拍」）。

**回滚成本**：**最低**（框架零改动；桥侧新增一条工作线程 + 一个计数）。

**承重假设**：

1. 假设「所有重订阅者都是本仓的桥」——F-06 的原话是「采用方只能自己再包一层（自己在订阅回调里 spawn，自己管生命周期）」⇒ 本案把坑原样留给**每一个外部采用方**，框架层未踩平 ⇒ 与 issue 意图（框架层踩平）**相悖**。
2. 若要检出跳拍，需要框架暴露状态版本 ⇒ 已经在长出案 C 的最小形态（「只加版本号」）。
3. 桥侧自建线程 ⇒ 每个采用方各写一遍（重复实现），违反「同类问题不造第二套解法」。

**与 M1/M5 交叉**：桥侧计数只是「我处理过几拍」，不是框架侧水位 ⇒ 检出跳拍需要框架版本号 ⇒ 收敛到案 C 的 X1=② 变体。

**什么条件下它更优**：若采用方只要「桥别把 drain 线程堵住」这一个目标，且不愿意引入新契约面——案 D 是**当天的最小止血**。

**我猜 D 最可能错在哪**：以为「桥自管就够了」。外部采用方（真正的目标用户）拿不到桥的代码，只会拿到「回调在 dispatch 线程同步执行」这句契约。

## 5. 推荐

**推荐案 C（两档并存 + 状态水位信号）**，并把 **案 D 作为「桥侧先行」的临时止血**（不作为终态）。

**推荐理由（三条，按权重）**：

1. **它唯一同时满足 A1/A2/A4/M1/M5 而不动既有语义**——排空环内零用户代码、投递 O(1)、载荷状态化、版本号内建；且 `Store` 六方法、审计链、通知序、回灌预算**全部零改动**（回滚成本最低）。
2. **它把「消费侧归属」留给宿主**（C7：框架不拥有循环）。框架不新增线程 ⇒ 不引入线程生命周期、join 序、队列背压、未消费丢弃这四类新失败面（正是案 B 的代价来源）。
3. **它与 ViewBridge 已有的 resync 机制同构**：桥的 `snapshot_doc()` 重同步正是 M5 的「版本跳跃即重取」；案 C 只是把版本号从「桥内部代数」提升为「框架状态水位」，两侧机制对齐而非新增。

**为什么不是案 A**：它解决的是「环体不被阻塞」，而 F-06 的实测痛点（审计 F-06 段 + QAS 度量 ①）是 dispatch 延迟被订阅者支配；且它丢了 F5 的回灌预算护栏、破了 F10 的审计链断言——**破坏面换不来收益**。

**为什么不是案 B**：异步 ≠ 线程 + 队列。案 B 把 M1 判定为缺陷的事件流形态引入框架，并附带 ≥4 类新失败面；在「状态信号」语义下这些问题**不存在**。

**为什么案 D 只是止血**：它让「桥」不堵 drain，但 F-06 的原话是采用方无路可走；且桥侧自建线程 = 每个采用方各写一遍。案 D 与案 C 不冲突（D 是 C 的「只加版本号」子集），可作为过渡。

### 5.1 证伪条件（出现这些事实就改推）

| 事实 | 改推 |
|---|---|
| ≥3 个真实采用方要求「框架把确切快照推给我」（不接受拉取） | 案 C 的 X1=③ 变体（发 `Arc<S>` + 版本号），并同步裁决 §6.4 落位策略 |
| 消费侧普遍为「单次动作后立即取一次」的低频模式，且延迟预算 < 100 µs | 案 B 的**单泵**变体（框架一条泵线程 + 每订阅者单槽 latest-value，X1=③）——但必须先证明 M1 合规（单槽=状态化，非事件流） |
| 宿主全是 tokio 生态 | 在 infra 侧提供 tokio 版投递口实现（`tokio::sync::Notify`/`mpsc`），**契约面不变**（案 C 的可替换组件留位） |
| 实测异步档让无订阅 dispatch 从 77 ns 退化 > 10 ns | 复核门控实现（版本自增与投递必须门控），必要时把版本自增移到「有异步订阅者时」 |
| 发现「拉取式」导致消费侧持有 `Arc<S>` 跨越落位 ⇒ F9 深克隆税在真实负载下显形 | §6.4 的落位策略裁决提前执行（每拍新 `Arc`） |

## 6. 落成交付骨架

### 6.1 选型

- 契约层（`skeleton`，零依赖）：新增 `notify` 模块 —— `NotifySink`（宿主实现）+ `Notify<S>`（实现方实现）+ 复用 `Subscription<S>` 票据（`skeleton/src/lib.rs:314-336`，`Subscription::new` 已是公开构造器，**不新增票据类型**）。
- 实现层（`skeleton-infra`，`runtime` feature，零三方）：`SyncStore` 实现 `Notify<S>`；新增状态版本计数器；新增异步订阅注册表；通知段新增「异步投递」分支（**排在同步回调之前**，见 6.3）。
- 复用面：`Store::snapshot()`（既有拉取面，F1 契约 2）、`Subscription<S>`（票据）、`audit_emit` 的「回调取出锁外调用 + 归还」模式（`skeleton-infra/src/runtime/audit_emit.rs:71` 取回调 → `:76-93` 锁外调用 → `:95-103` 归还）、`audit_gate` 的「无订阅者一次 load 即返」快路径（`audit_emit.rs:56-58`，门控范式）。

### 6.2 骨架契约（语义承诺写进 doc，不是写进实现）

| 承诺 | 内容 | 判据 |
|---|---|---|
| N1 | 投递口 `publish` 在排空环内被调用，**框架不在其后执行任何用户代码** | A1 |
| N2 | `publish` 必须 O(1) 返回；宿主实现方需自行保证（框架不强制，只能靠契约 + 文档） | A2 |
| N3 | 版本号单调递增，每拍快照落位 +1；宿主按版本号检出跳拍并重取 | A3/A4/M5 |
| N4 | 允许合并；**框架不承诺逐拍投递**（与 M1 一致） | A4/M1 |
| N5 | 投递口 panic ⇒ 捕获、摘除该投递口、计入 `subscriber_panics` + 成因摘要（复用既有读侧） | A5/C4 |
| N6 | 闭门后登记：计数进 `subscriptions_after_close`，永不发信号 | A6 |
| N7 | 异步档与同步档**并存**，两者互不影响；同步档回调仍在 dispatch 线程（既有契约不变） | C3/C6 |
| N8 | 异步档**不外发 `Arc<S>`**（只发版本号）⇒ 框架不在通知路径上制造快照持有者 | §6.4 |

### 6.3 数据走向（含顺序决策）

```
drain_owned 循环（每拍）:
  reduce → place_snapshot(state_version += 1) → forward_effects
    → 通知段:
        ① 异步档：逐个投递口 publish(state_version)   ← 先发，O(1)
        ② 同步档：现有 subscribe 回调（原地执行）+ 现有 subscribe_local（TLS）
        ③ 审计：现有 Notified 节点（语义不变）
```

**为什么异步投递排在同步回调之前**：若同步档里有慢订阅者，异步消费者的可见延迟会被它连带拖后（违反 QAS 响应度量 ③ 的「延迟来自消费侧调度」）。把 O(1) 的异步投递前置，使异步档的延迟只受消费线程调度影响。**该顺序变更不影响同步档内部既有顺序**（本地先行、跨线程随后，文档 `runtime.rs:670-673`），也不影响审计链（F10 的 `Notified` 仍在通知段末尾）。

**为什么版本号在落位时自增**（而不是通知时）：版本号必须与「这一拍的状态」一一对应；落位是状态唯一变化的时刻 ⇒ 版本号 = 状态代数。零异步订阅者时不自增（门控，照抄 `audit_gate` 先例：`audit_emit.rs:56-58` 一次 Acquire load 即返）⇒ 77 ns 锚不受影响。

### 6.4 落位策略的联动裁决（必须显式拍板的一处）

F9：`place_snapshot` 用 `Arc::make_mut` 就地改写 ⇒ **任何跨拍持有 `Arc<S>` 的外部者会让下一拍深克隆 `S`**（F6：1 MiB State ≈ 210 µs/dispatch）。

- 异步档只发版本号（N8）⇒ 框架侧不制造持有者；但消费侧 `snapshot()` 拉取后若跨拍持有，仍会触发同样的深克隆。
- **裁决选项**：
  - **(a) 维持 `Arc::make_mut` 不变**：消费侧自律「拉取后尽快释放」（写进消费侧纪律 + 桥侧文档）。零框架改动，但真实负载下可能复发 F-05 的税。
  - **(b) 落位改为每拍新 `Arc`**（`*slot = Arc::new(next_val)`）：外部持有者**永不**触发深克隆，代价是每拍一次 `Arc` 堆分配（需重测 77 ns 锚，可能落在 ~100 ns 契约边界）。**这是本稿唯一触碰热路径的选项**，需要实测数据支撑后再拍。
  - **(c) 双缓冲/epoch**：复杂度高，不预付。

**建议**：先 (a)，把 (b) 作为「实测出现深克隆税」时的升级路径写进 ADR 触发条件。

### 6.5 目标环境实例化（三种宿主形态）

| 宿主 | 消费侧形态 | 框架面 |
|---|---|---|
| 帧循环宿主（Unity/游戏循环） | 帧内检查版本号，变化则 `snapshot()` → 渲染 | 只用 `subscribe_notify` + `snapshot()` |
| tokio 宿主 | `publish` 内 `tokio::sync::Notify::notify_one()` 或 `mpsc::Sender::try_send(version)` | 同上（投递口由宿主实现，框架零 tokio 依赖，守 C2） |
| 服务/worker 宿主 | worker 线程轮询版本号或收信号 | 同上 |

**框架侧在三种形态下完全一致**——这正是「状态信号 + 拉取」比「推送快照」更可复用的原因（也是 X1=② 相对 X1=① 的主要收益）。

### 6.6 可替换组件留位（契约不换，机器可换）

| 组件 | 留位方式 | 何时填 |
|---|---|---|
| 投递口实现 | `NotifySink` 由宿主实现 | 立即（宿主自选） |
| tokio 版投递口 | infra `tokio` feature 下提供 `NotifySink` 的 tokio 实现 | 宿主为 tokio 生态时 |
| 快照载荷变体（X1=③） | `NotifySink::publish` 增参 `Option<Arc<S>>` 或另开 trait | §5.1 证伪条件触发时 |
| 桥侧 resync | 复用 ViewBridge 既有 `snapshot_doc()` 机制 | 已在 ViewBridge 方案内 |

## 7. 与 ViewBridge 的交叉（M1 / M5）

**ViewBridge 现状**（`docs/research/mvi-view-bridge-research.md` §3.2）：桥以 `store.subscribe` 挂载，**通知体内做投影 + eager 区域编码**（`region_version`/`region_encodes` 计数即为此设）⇒ 桥本身就是 F-06 的**第一个受害者**——投影与编码成本直接进排空环。

| 交叉点 | 影响 | 处理 |
|---|---|---|
| 桥的通知体重活 | 投影 + 区域编码进 drain 线程 ⇒ 排空环被桥拖慢 | 桥改挂 `subscribe_notify`：投递口只做 O(1) 信号；投影与编码搬到**宿主消费侧** |
| 桥的「共享区始终最新」承诺（研究文档 §3.1/§3.6：eager 编码，共享区必须始终最新，否则 UI 读到旧值） | 异步化后「最新」的含义变为「**至最近一次消费为止**的最新」 | 必须重述为「至消费点为止最新」+ **版本号进区域头**（`Header.version` 已有版本位）⇒ UI 凭版本判新鲜度（M5）。**这是 eager 语义与异步通知的正面冲突，必须在 ViewBridge ADR 里显式记账，不得含糊** |
| 桥的 JSON 补丁通道版本 | M5 抄录清单第 3 条要求 `PatchBatch` 带版本 | 异步档的 `state_version` 正好作为该版本来源 ⇒ 两处版本号应**同源**（否则撕裂判定失真） |
| 桥的 M1 纪律（上行只许状态化，不做一次性事件流） | 异步通知若做成事件流会与桥的上行纪律冲突 | 案 C 载荷 = 状态信号 ⇒ 与 M1 同向，无冲突 |
| 桥的并发契约（研究文档 F1 修复：桥内态 `Arc<Mutex<..>>`、`ViewBridge: Send + Sync`、通知体在 dispatch 线程、pull 侧任意线程） | 异步化后「通知体在 dispatch 线程」对桥不再成立 ⇒ 桥的投影从「dispatch 线程内」变为「宿主消费线程内」 | 桥的 `core` 锁竞争方从「dispatch 线程 vs pull 线程」变为「消费线程 vs pull 线程」⇒ 锁窗声明需改（研究文档 §3.2 同步形态选择段） |
| 桥的投影 panic 毒化 → resync 闭环 | 不变（毒化位在桥内） | 但「毒化发生在消费线程」需写进桥的 ADR |

**结论**：案 C 与 ViewBridge **同向**（都是「状态 + 版本」纪律），但要求 ViewBridge 侧改三处措辞/承诺（eager 最新性语义、版本号同源、通知线程归属）。案 A 与 ViewBridge **正面冲突**（A 改变通知时刻 ⇒ 桥的逐拍交错前提变化）。案 B 与 ViewBridge 冲突较轻（桥仍在框架线程执行投影），但引入框架线程，与 C7 张力。

## 8. 规范落点（逐条）

| 规范 | 落点 |

## 9. 失败模式与恢复路径

| # | 失败模式 | 框架侧行为 | 恢复路径 |
|---|---|---|---|
| FM1 | 投递口 `publish` panic | `catch_unwind` 捕获 → 摘除该投递口 → `subscriber_panics` +1 + 成因摘要 | 摘除即失效（同同步档 fail-closed 纪律）；宿主可重新登记 |
| FM2 | 投递口 `publish` 阻塞/极慢 | 框架**无法检测也无法阻止**（N2 是契约义务） | 宿主侧自律；文档明示；实测若普遍发生 ⇒ 触发 §5.1 证伪（改案 B 单泵变体） |
| FM3 | 消费侧合并丢拍 | 框架不感知（合并是宿主侧行为） | 版本号让消费侧检出跳拍 → 重取现态（M5，桥已有 resync 机制） |
| FM4 | 闭门后登记投递口 | 计数 `subscriptions_after_close` +1，**永不发信号** | 与同步档一致（审计 F-10 的既有取舍，读侧可见） |
| FM5 | store 提前 drop | 投递口随注册表消亡；宿主持有版本号但不再收到信号 | 宿主经 `is_closed()`/投递口断连感知（**投递口断连是否可感知需在契约里定**：建议宿主投递口实现里能观察到「不再有新版本」——本稿列为未决问题 Q3） |
| FM6 | 订阅者回调内 dispatch 造成环 | **不受影响**（同步档语义与回灌预算完全不动） | 既有 64 预算 + `feedback_budget_exceeded` 计数 |
| FM7 | 版本号与快照不一致（消费侧读到旧态） | 消费侧按「版本号 + 拉取」两步，中间可能跨拍 | 版本号判定：拉取后版本已变 ⇒ 重取（M5 纪律，桥已有同款） |
| FM8 | 消费侧长期持有 `Arc<S>` | 框架不感知；下一拍落位走 `Arc::make_mut` 克隆分支 ⇒ F5 深克隆税 | §6.4 裁决 (a)/(b)；消费侧自律「拉取后尽快释放」 |

## 10. 风险与证伪（半年后这套结构最可能在哪里疼）

| 风险 | 症状 | 早期信号 | 缓解 |
|---|---|---|---|
| R1 「拉取式」不被采用方接受 | 大量采用方绕过框架自建推送 | 采用方在采用方群里自己写 `thread::spawn` | 准备 X1=③ 变体（推快照 + 版本），并先裁决 §6.4(b) |
| R2 版本号与桥/其他模块的代数分裂 | UI 见到版本跳跃却无法判定该重取 | 桥的 `PatchBatch.version` 与 `state_version` 不等 | 单一来源：桥的版本号取自 `state_version`（本文 §7 已要求同源） |
| R3 门控写错 ⇒ 77 ns 锚退化 | 无订阅 dispatch 变慢 | `examples/dispatch_profile.rs` 实测退化 | 版本自增与投递全部走「有异步订阅者」闸；CI 加锚断言 |
| R4 契约层词汇膨胀 | `skeleton` 公共面变大，采用方升级成本上升 | 有人开始「抄框架自己写一套」 | 新端口独立于 `Store`（C3）；不扩 `Store` 六方法；`NotifySink` 方法数 = 1 |
| R5 同步档仍被误用为重活通道 | 慢订阅者照样堵 drain，采用方抱怨「异步化没解决」 | 线上 dispatch 延迟毛刺与订阅者耗时相关 | 契约文案强写「同步回调须廉价；重活走异步档」；可选在审计面加「同步回调耗时」读侧（本稿不预付，列为二期） |
| R6 文档口径漂移 | README/reference/ADR 三处说法不一致（审计 F-01/F-02 同型） | 评审发现措辞冲突 | 落地时按 §8 三处对账清单逐条核 |

## 11. 我猜最可能错在哪（三条，供实施与复盘对照）

1. **「状态信号 + 拉取」对「需要确切快照」的采用方不够用**——我赌这会是最常见的反需求；备好 X1=③ 变体，别到时候临时改契约。
2. **门控与版本自增的性能实现**——我赌实现期最容易在这里翻车（77 ns 锚是本仓的自尊心）。版本自增必须与「有异步订阅者」同闸，否则每拍一次 `fetch_add` 就够抵消一部分收益。
3. **ViewBridge 的 eager「始终最新」承诺与异步化正面冲突**——我赌这条会在 ViewBridge ADR 评审时被 momus 打回；本文已把它列为必须显式记账的冲突项，而不是含糊带过。

## 13. ADR 草稿（编号 0008，**已成文**：`docs/adr/0008-async-notify-signal.md`）

> 沿 ADR 0005 体例（MADR 轻量五节）。本节草稿已拍板并成文为 `docs/adr/0008-async-notify-signal.md`（**以该 ADR 为定案文本**；本节保留为草稿留痕）。

### 13.1 Status

已采纳（2026-10-27，用户拍板）——成文见 `docs/adr/0008-async-notify-signal.md`。关联 `docs/adr/0004-std-ext-split.md`（分层纪律）、`0005-journal-reshape.md`（破坏性直迁先例）；关联设计稿 `docs/research/async-notification-design.md`。

### 13.2 Context

- F-06：订阅回调在 dispatch 线程同步执行（`skeleton/src/lib.rs:373`、`skeleton-infra/src/runtime.rs:1081`），慢订阅者阻塞整个状态机；审计实测 1 MiB State 的深克隆 ≈ 210 µs/dispatch（F-05）。
- 现有同步语义被三处钉死：回灌深度预算（`runtime.rs:241`）、审计交错链（`tests/journal_port.rs:305-330`）、通知序可观测（`tests/store_behavior_gaps.rs:225-243`）。
- 外部判据：M1（不用不保证投递的事件流）、M5（帧/拍级一致的水位与版本）。

### 13.3 Decision

**采纳「两档并存 + 状态水位信号」通知面：**

1. 现有 `Store::subscribe`（同步档）与 `SyncStore::subscribe_local`（本地档）**语义一字不改**（零破坏、零回滚成本）。
2. 新增独立契约端口（`skeleton/src/notify.rs`）：`NotifySink`（宿主实现的 O(1) 投递口）+ `Notify<S>`（实现方实现的登记面），票据复用 `Subscription<S>`。
3. 载荷 = **单调状态版本号**（每拍快照落位 +1）；消费侧按需 `store.snapshot()` 拉取；合并合法且**必须按版本号检出跳拍并重取**（M5）。**不提供事件流形态**（M1）。
4. 排空环内对异步档只做 O(1) 投递，**不执行任何用户重活**；异步投递排在同步回调之前（使异步档延迟只受消费线程调度支配）。
5. 失败面复用既有读侧：投递口 panic ⇒ `subscriber_panics` + 成因摘要（摘除该投递口）；闭门登记 ⇒ `subscriptions_after_close`；新增唯一读侧 `notify_published()`（投递次数）。
6. 快照落位策略本期**不变**（`Arc::make_mut`）；「消费侧跨拍持有 `Arc<S>` ⇒ 深克隆税」的升级路径（每拍新 `Arc`）写为触发式后续项。
7. `Store` 六方法承诺不动；新增能力走独立端口（守「六方法即全契约」）。
8. `runtime` feature 依赖树不变（零新三方）。

### 13.4 Consequences

**正向**：

- 排空环内用户代码执行时间结构性归零（A1）；投递 O(1) ⇒ 慢订阅者不再传导到 dispatch 延迟（QAS 度量 ①②）。
- 既有契约、审计链、通知序、回灌预算**零改动** ⇒ 既有测试全部不动，回滚成本 = 删新增文件。
- 载荷状态化 ⇒ 与 M1 同向；版本号内建 ⇒ 与 M5 同源（ViewBridge 的 `PatchBatch`/区域头版本可取同一来源）。
- 框架不新增线程 ⇒ 不引入线程生命周期/join 序/队列背压/未消费丢弃四类新失败面；守 C7。

**负向 / 代价**：

- 消费侧要自己写「信号 → 拉取 → 处理」循环（采用方多写几行）；不提供「框架替你推确切快照」。
- 合并丢拍对消费侧是常态（须靠版本号检出）——不懂这一点的采用方会看到「少了几次更新」。
- 同步档**不受益**：慢同步订阅者照样堵 drain（须靠契约文案引导迁移）。
- 版本号与桥/其他模块的代数必须同源，否则撕裂判定失真（R2）。
- 本地档仍不同步（跨线程 dispatch 不触达本地订阅，F-09 仍在）——本次不修。

**破坏性变更清单**（0.1.0 未发布，零兼容负担）：

| 项 | 旧 | 新 |
|---|---|---|
| `skeleton` 公共面 | 无异步通知端口 | 新增 `notify` 模块（`Notify` / `NotifySink`），`Store` 不变 |
| `SyncStore` | 无异步通知面 | 实现 `Notify<S>`；新增 `notify_published()` 读侧；新增 `state_version` 内部计数器 |
| 既有订阅语义 | 同步回调在 dispatch 线程 | **不变** |
| 依赖树 | `runtime` 零三方 | **不变** |

### 13.5 Verification（拍板后实现期可执行）

1. `cargo test -p udf-skeleton-infra --all-features` 全绿且**既有通知/审计/回灌测试未修改**（零破坏的证明方式：diff 中这些测试文件零改动）。
2. 新增 `tests/async_notify.rs` 六项断言（§8 测试策略 ①–⑥）。
3. `cargo run -p udf-skeleton-infra --example dispatch_profile --features runtime`：无订阅 dispatch 不回退 77 ns 锚（门控正确性）。
4. `cargo tree -p udf-skeleton-infra -e normal` 零三方口径不变。
5. 手工验收：一个「回调 sleep 50 ms」的**异步**投递口挂上后，dispatch 延迟保持 ~100 ns 量级（重活确实不在环内）。
