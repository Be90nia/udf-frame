# MVI UI 解耦——澄清记录（2026-10-27）

## 用户原话（关键三段）

1. 「我想用映射的方式和派生的方式来解决架构与项目的耦合性太强的问题..你看看怎么弄会更好..性能和内存都会更优秀你看看怎么弄」
2. 「正常来说我们项目用的MVI架构模式..必定在UI端会有很严重的耦合问题..为了降低耦合性我就想用映射和派生的方式来降低他们的耦合..如果你有更好的办法也可以提出来」
3. 「我想udf是一个通用型架构..就是说谁的项目都能用..然后这个映射和派生都要在我们rust内部直接做好..然后UI是用什么技术语言都没有关系..只要他绑定好要获取的数据就能拿到这些数据..这是我想要的效果..这样做解耦效果应该会好很多吧??」

## 拍板结论

| 项 | 决定 |
|---|---|
| 范围 | udf-frame 内置**语言无关视图数据面**：映射（State→视图数据）+ 派生（派生数据）在 Rust 侧完成；UI 任意语言/技术栈，按绑定取数 |
| UI 栈 | 用户未指定（无）；设计必须工具栈无关，headless 验收 |
| 验收 | 用户选择「先出方案」——方案过审后再定验收口径 |
| 否决项 | 字符串路由/事件总线（框架哲学封死：compose.rs「字符串路由组合的封死形态」） |

## 事实账本

- ✅ UI 耦合三处：Driver/subscribe 下行全量领域 State；UI 手拼嵌套 Action 树；无 diff 闸全量重渲
- ✅ 外部对标：Yew use_reducer_eq（diff 闸）/ Bevy blanket impl / Druid derive(Data) 被作者否定 / Tauri·Slint（Rust 核心 + 任意 UI 语言）——报告 `reports/2026-10-27-derive-decoupling-precedents.md`
- ✅ std-ext json 域（严格 RFC 8259 解码）已落，commit 3101d21
- ✅ 仓库内无既有视图投影词汇（ViewModel/ViewState/Intent 全查无）
- 🔍 std-ext json 域编码能力待查（影响桥的出站面设计）
- ⚠️ 假设：绑定粒度按路径寻址、更新以补丁形式外送；派生=声明式派生数据（输入不变不重算）——待 architect 方案定稿确认

## 性能/内存收益的真实来源（汇报口径）

diff 闸 + 只投影子集 + 派生记忆化 + 补丁增量，不是来自「派生宏」本身（静态代码生成，性能中性）。
